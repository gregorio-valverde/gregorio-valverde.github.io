## How the Data Platform scales

Project growth follows a consistent sequence:

1. Define the raw structure in a YAML file.
2. Implement the extractor for the new source.
3. Register the pipeline with its connection and options.
4. Add the dbt source, models, tests, and documentation.
5. Associate the models with the tag executed by the DAG.

A pipeline configuration contains only source-specific information:

```python
{
    "pipeline_id": "employees",
    "yaml_path": "/usr/local/airflow/include/elt/config/src/src_hr_employees.yml",
    "extractor": extract_src_hr_employees,
    "conn_id": "dw_postgres",
    "sync_enabled": True,
    "load_mode_default": "full_refresh",
    "enabled": True,
}
```

The factory uses this definition to automatically create run gating, destination synchronization, extraction, raw loading, and the downstream `dbt build` dependency.

## Operational guarantees

- A successful rerun with the same input leaves the same raw state instead of accumulating the previous batch again.
- `max_active_runs=1` prevents two demonstration DAG runs from modifying the same tables simultaneously.
- `include_pipelines` and `exclude_pipelines` execute a subset of sources without changing code.
- Independent TaskGroups allow pipelines to run in parallel up to the limit defined by `max_active_tasks` or an Airflow pool.
- Tag-selected `dbt build` runs after raw loading and combines model construction, tests, and dependency order in one command.

## Environment configuration

The same pattern supports behavior changes without modifying the main class:

- Retries and alerts through Airflow `default_args`.
- Scheduling through a cron expression.
- Global or pipeline-specific connections.
- Separate dbt targets for development and production.
- Destination databases selected through connections and environment variables.

The public demonstration uses the `dev` target, manual execution, zero retries, and disabled email notifications. These are configurable options rather than factory limitations.

## Quality and documentation in dbt

`sources.yml` documents raw sources and applies declarative tests such as `not_null`, `unique`, `relationships`, and `accepted_values`. Staging then performs casting, cleaning, and normalization through views. Final models are materialized as dimension and fact tables.

The `schema.yml` documentation defines the purpose, grain, relevant columns, and relationships of each final model. The repository therefore keeps both the transformation and its analytical contract together.

## Next evolution: observability

The natural next layer would persist Airflow metadata and dbt artifacts in audit tables: duration, processed rows, states, retries, test results, and freshness. Grafana could consume those metrics to analyze historical reliability and performance.

This is presented as a possible evolution, not as an already implemented repository feature.
