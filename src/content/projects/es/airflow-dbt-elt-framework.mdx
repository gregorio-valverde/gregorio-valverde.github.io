## Cómo se amplía la Data Platform

El crecimiento del proyecto sigue una secuencia constante:

1. Definir la estructura raw en un archivo YAML.
2. Implementar el extractor para el nuevo origen.
3. Registrar el pipeline con su conexión y sus opciones.
4. Añadir el source, los modelos, los tests y la documentación de dbt.
5. Asociar los modelos a la etiqueta que ejecutará el DAG.

Una configuración de pipeline mantiene únicamente la información específica del origen:

```python
{
    "pipeline_id": "employees",
    "yaml_path": "/usr/local/airflow/include/elt/config/src/src_hr_employees.yml",
    "extractor": extract_src_hr_employees,
    "conn_id": "dw_postgres",
    "sync_enabled": True,
    "load_mode_default": "full_refresh",
    "enabled": True,
}
```

La fábrica utiliza esa definición para crear automáticamente el control de ejecución, la sincronización del destino, la extracción, la carga raw y la dependencia con `dbt build`.

## Garantías operativas

- Una repetición correcta con la misma entrada deja el mismo estado raw, sin acumular de nuevo el lote anterior.
- `max_active_runs=1` evita que dos ejecuciones del DAG modifiquen simultáneamente las mismas tablas en la demostración.
- `include_pipelines` y `exclude_pipelines` permiten ejecutar solo una parte de las fuentes sin cambiar el código.
- Los TaskGroups independientes permiten paralelizar pipelines hasta el límite definido por `max_active_tasks` o por un pool.
- `dbt build` se ejecuta por etiqueta después de las cargas raw y combina construcción, tests y dependencias en un único comando.

## Configuración por entorno

El mismo patrón admite cambios de comportamiento sin modificar la clase principal:

- Retries y alertas mediante `default_args` de Airflow.
- Planificación mediante una expresión cron.
- Conexiones globales o específicas por pipeline.
- Targets de dbt separados para desarrollo y producción.
- Bases de datos de destino seleccionadas mediante conexiones y variables de entorno.

La demostración pública utiliza el target `dev`, ejecución manual, cero retries y correos desactivados. Son opciones configurables, no limitaciones de la fábrica.

## Calidad y documentación en dbt

`sources.yml` documenta las fuentes raw y aplica tests declarativos como `not_null`, `unique`, `relationships` y `accepted_values`. A continuación, staging realiza tipado, limpieza y normalización mediante vistas. Los modelos finales se materializan como dimensiones y hechos en tablas.

La documentación de `schema.yml` deja definidos el propósito, el grano, las columnas relevantes y las relaciones de cada modelo final. De este modo, el propio repositorio conserva tanto la transformación como su contrato analítico.

## Siguiente evolución: observabilidad

La siguiente capa natural sería persistir metadatos de Airflow y artefactos de dbt en tablas de auditoría: duración, filas procesadas, estados, retries, resultados de tests y frescura. Estas métricas podrían consumirse desde Grafana para analizar fiabilidad y rendimiento histórico.

Esta parte se presenta como evolución posible y no como funcionalidad ya implementada en el repositorio.
